Étude de cas du cours : évaluation pondérée

Valeurs lues sur un logiciel X : commentaires 10 sur 100, noms de variables incompréhensibles, complexité 3, nombre de lignes par module entre 50 et 100. Notes possibles : 2, 1, 0.

MétriqueMesureNote 2Note 1Note 0
Commentaires10 %[100 ; 20]]20 ; 10]]10 ; 0]
Noms de variablesIncompréhensiblesSignificatifsMoyensIncompréhensibles
Complexité3[0 ; 3]]3 ; 5]]5 ; ...]
Lignes par moduleentre 50 et 100[0 ; 50]]50 ; 100]]100 ; ...]

Pondérations : Auto-documentation = 0,5 Commentaires + 0,5 Noms. Simplicité = 0,4 Commentaires + 0,4 Complexité + 0,2 Lignes. Maintenabilité = 0,6 Simplicité + 0,4 Auto-documentation. Fiabilité = 1 × Simplicité.

Solution détaillée
  1. Arborescence : Qualité, puis deux facteurs (Maintenabilité, Fiabilité). Maintenabilité a deux critères (Simplicité, Auto-documentation). Fiabilité a un critère (Simplicité). Chaque critère a ses métriques : Auto-documentation (Commentaires, Noms), Simplicité (Commentaires, Complexité, Lignes).
  2. Notes des métriques : Commentaires 10 % est dans ]20 ; 10] donc 1. Noms incompréhensibles donc 0. Complexité 3 est dans [0 ; 3] donc 2. Lignes 50 à 100 est dans ]50 ; 100] donc 1.
  3. Critères : Auto-documentation = 0,5 × 1 + 0,5 × 0 = 0,5. Simplicité = 0,4 × 1 + 0,4 × 2 + 0,2 × 1 = 0,4 + 0,8 + 0,2 = 1,4.
  4. Facteurs : Maintenabilité = 0,6 × 1,4 + 0,4 × 0,5 = 0,84 + 0,2 = 1,04. Fiabilité = 1 × 1,4 = 1,4.
  5. Qualité mesurée : moyenne des deux facteurs (poids égaux) = (1,04 + 1,4) / 2 = 1,22.
  6. Qualité totale : la note maximale possible est 3, donc 1,22 / 3 ≈ 40,7 %. Le logiciel est en dessous de la moyenne : améliorer d'abord la lisibilité des noms et le nombre de commentaires.

Le cours ne définit pas explicitement « qualité mesurée » et « qualité totale ». Mon interprétation : mesurée = moyenne pondérée des facteurs, totale = rapport à la note maximale en pourcentage. Écrivez votre définition en tête de réponse.

TD1 : autopsie d'un échec logiciel

Consigne : choisir un cas, puis rédiger un rapport d'une page en PDF : présentation, chaîne causale (erreur, défaut, défaillance), impacts, mesures SQA liées aux phases du SDLC, références.

Rapport modèle : Mariner 1 (1962)

1. Présentation du cas

Mariner 1 est la première sonde du programme Mariner, lancée le 22 juillet 1962 pour survoler Vénus. Domaine : aérospatiale, calcul de trajectoire et guidage.

2. Chaîne causale

ÉtapeConstat
Erreur (humaine)Un programmeur a mal transcrit une formule manuscrite en code (erreur de transcription, symbole manquant).
Défaut (dans le produit)L'équation implémentée dans le logiciel de guidage ne correspond pas à la formule voulue : mauvaise estimation de la trajectoire.
Défaillance (en exploitation)La sonde dévie de sa trajectoire et est détruite environ 294,5 secondes (5 minutes) après le décollage.

3. Impacts

  • Financier : 18,5 millions de dollars, mission perdue.
  • Humain et opérationnel : mission scientifique vers Vénus manquée (sonde sans équipage, d'après le cours aucune perte humaine n'est citée).
  • Réputation et juridique : atteinte à la crédibilité du programme. Aucune conséquence juridique n'est mentionnée dans le cours.

4. Mesures SQA reliées au SDLC

PhaseMesure qui aurait prévenu ou détecté le problème
Exigences et spécificationFormules validées et signées par les scientifiques, spécification sans ambiguïté, traçabilité formule vers code.
ConceptionRevue de conception du module de trajectoire, par un relecteur indépendant.
CodageRevue de code par les pairs et double vérification de chaque transcription de formule, standards de codage.
TestsTests unitaires et simulations de trajectoire sur des cas connus, comparaison avec des valeurs de référence.
ExploitationSurveillance de la trajectoire et procédure de correction en vol.

Principe : plus on détecte tôt, moins l'erreur coûte cher. Chaque mesure est une pratique d'assurance qualité indépendante de l'équipe de développement (objectivité de la SQA).

TD3 : McCabe et Halstead sur calcul_moyenne

def calcul_moyenne(liste):
    # Ceci est un commentaire.

    total = 0
    nombre_elements = 0

    for element in liste:
        total += element
        nombre_elements += 1

    if nombre_elements == 0:
        return 0
    else:
        return total / nombre_elements

Partie 1 : métriques de code (LOCphy, LOCpro, LOCcom, LOCbl, DC)

Solution

On compte les lignes du bloc tel qu'il est écrit : 14 lignes.

  • LOCphy = 14.
  • LOCbl = 3 (une après le commentaire, une après nombre_elements = 0, une après la boucle).
  • LOCcom = 1 (la ligne « # Ceci est un commentaire. »).
  • LOCpro = 14 - 3 - 1 = 10.
  • DC = LOCcom / LOCphy = 1 / 14 ≈ 0,07 (7 %).

Interprétation : DC est bien inférieure à la norme 0,2 à 0,3, la fonction est très peu commentée. Les lignes vides représentent 3 / 14 ≈ 21 %, un peu au-dessus de la plage de 10 à 20 %. Si vous ne comptez pas la dernière ligne ou comptez autrement la ligne « def », vos chiffres varient d'une unité : précisez votre règle de comptage.

Partie 2 : complexité de McCabe

Solution

Décisions : le for (1) et le if (1). Le else ne compte pas. π = 2, donc C = π + 1 = 3.

Vérification avec le graphe de contrôle :

  • Nœuds : 1 initialisations (total, nombre), 2 test du for, 3 corps de la boucle, 4 test du if, 5 return 0, 6 return total / nombre, 7 sortie. N = 7.
  • Arcs : 1 vers 2, 2 vers 3, 3 vers 2, 2 vers 4, 4 vers 5, 4 vers 6, 5 vers 7, 6 vers 7. E = 8.
  • V(G) = E - N + 2P = 8 - 7 + 2 = 3.

Les deux méthodes donnent 3 : trois chemins indépendants (liste vide, liste non vide avec boucle, et le cas du if), donc au moins 3 cas de test.

Partie 2 bis : métriques de Halstead

Solution (règle de comptage indiquée)

Règle de comptage retenue : les mots-clés (def, for, in, if, else, return), les symboles (=, +=, ==, /, deux-points) et la paire de parenthèses () sont des opérateurs. Les noms, les nombres et les constantes sont des opérandes. Le commentaire est ignoré. L'énoncé du TD inverse les noms n et N ; j'utilise ceux du cours : n est le vocabulaire, N la longueur.

Opérateurdef():=forin+=if==returnelse/
Occurrences114211211211
Opérandecalcul_moyennelistetotal0nombre_elementselement1
Occurrences1234421

n1 = 12, N1 = 18, n2 = 7, N2 = 17.

  • Vocabulaire n = 12 + 7 = 19. Longueur N = 18 + 17 = 35.
  • Volume V = 35 × log2(19) = 35 × 4,248 ≈ 148,7 bits.
  • Longueur estimée N* = n1 log2(n1) + n2 log2(n2) = 12 × 3,585 + 7 × 2,807 ≈ 62,7 (formule de Halstead usuelle, absente de vos slides).
  • Difficulté D = (12 / 2) × (17 / 7) = 6 × 2,43 ≈ 14,57.
  • Effort E = V × D = 148,7 × 14,57 ≈ 2166.
  • Temps T = E / 18 ≈ 120 s (environ 2 minutes).
  • Bugs B = E^(2/3) / 3000 = 167,4 / 3000 ≈ 0,056.

Une autre règle de comptage donne d'autres nombres, mais le même ordre de grandeur. L'important est d'annoncer la règle et de l'appliquer partout.

Partie 3 : interprétation et comparaison

Solution
  • McCabe : V(G) = 3, dans la plage 1 à 10 : procédure simple, risque faible, 3 cas de test minimum.
  • Halstead : peu de bugs estimés (0,056), environ 2 minutes d'effort, difficulté moyenne (14,6) pour une fonction de 14 lignes.
  • Conclusion : la fonction est simple et facile à tester. Les deux mesures concordent.
  • Corrélation : les deux augmentent quand on ajoute des branches et des instructions, donc elles évoluent ensemble ici. Mais elles mesurent des choses différentes : McCabe compte les chemins d'exécution, Halstead compte le vocabulaire et la taille. Une fonction longue sans branche aurait un McCabe de 1 et un Halstead élevé.

Partie 4 : version optimisée

Solution
def calcul_moyenne(liste):
    return sum(liste) / len(liste) if liste else 0
  • La boucle for et les deux compteurs disparaissent : sum et len les remplacent. Il reste une seule décision (liste vide ou non).
  • McCabe : π = 1 (l'expression conditionnelle), donc C = 2 au lieu de 3.
  • Halstead (même règle de comptage) : opérateurs def, (), :, return, /, if, else : n1 = 7, N1 = 9 (() compte 3 fois). Opérandes calcul_moyenne, liste (4 fois), sum, len, 0 : n2 = 5, N2 = 8. Donc n = 12, N = 17, V ≈ 60,9, D = 3,5 × 1,6 = 5,6, E ≈ 341, T ≈ 19 s, B ≈ 0,016.
  • Gain : volume divisé par 2,4, effort divisé par 6,3, et une décision en moins.

Cas limite : « liste vide » est traité par la condition, comme avant (division par zéro évitée).

Partie 5 : réflexion

Solution

Pourquoi mesurer la complexité ? Pour estimer l'effort de test (nombre de cas de test selon McCabe), prévoir la maintenance et le risque de bugs, repérer le code critique, piloter les revues de code et fixer un seuil dans le plan qualité. Une complexité plus faible rend le code plus lisible, plus facile à tester et à corriger sans régression.

Limites :

  • McCabe ignore la complexité des données, l'imbrication des blocs et la lisibilité (c'est une raison d'être de la complexité cognitive de SonarQube). Un long switch donne un nombre élevé alors qu'il est facile à lire.
  • Halstead dépend des règles de comptage des opérateurs et opérandes, ignore la structure de contrôle, et ses constantes (18, 3000) sont empiriques.
  • Aucune des deux ne dit si le code est correct, bien conçu ou bien documenté. Il faut les combiner avec des tests, des revues et d'autres métriques.

Exercice 2 : analyse critique (méthode de réponse)

Solution
  • Classe la plus complexe : celle qui a le WMC le plus élevé. Justifier avec le nombre de méthodes et leurs complexités, et vérifier RFC et CBO.
  • Classe la plus cohérente : celle qui a le LCOM le plus bas (0 ou proche de 0).
  • Corrélation WMC et RFC : en général oui, plus de méthodes donne plus de réponses possibles (RFC compte les méthodes de la classe plus celles qu'elles appellent). Confirmer en comparant les colonnes classe par classe.
  • Risque de faible réutilisabilité : CBO élevé (fort couplage), LCOM élevé (faible cohésion), DIT élevé.
  • Package le plus stable : celui dont Ca est élevé et Ce faible (instabilité I = Ce / (Ca + Ce) proche de 0). Dans l'esprit du cours, le package model (Book, Lendable), dont dépendent les autres, doit sortir plus stable que service, à confirmer avec vos valeurs.

TP : analyse avec SonarQube

Méthode pas à pas
  1. Prérequis : Java 17 ou plus, SonarQube Community 25.10.0 ou plus, SonarScanner, projet gestion_Bib.
  2. Démarrer le serveur : dossier bin\windows-x86-64, lancer StartSonar.bat, ouvrir http://localhost:9000/.
  3. Créer le projet : nom, clé, branche principale, token (à copier dans un fichier séparé), Java et système d'exploitation.
  4. Préparer le code : tous les .java dans src/, compiler vers bin/, ouvrir sonar-project.properties et remplacer <VOTRE_TOKEN_SONAR> par le token.
  5. Lancer sonar-scanner.bat depuis la racine du projet et vérifier qu'il n'y a pas d'erreur.
  6. Lire le dashboard : bugs, code smells, duplications, vulnérabilités.

Q1 et Q2 : trois problèmes dans Book.java ou Library.java, pourquoi, quelle solution

Méthode de réponse

Ouvrez le projet dans le dashboard, onglet Issues, filtrez sur le fichier. Pour chaque problème, notez la règle, la gravité (bloquant, critique, majeur, mineur, info), la ligne, puis écrivez : pourquoi c'est un problème, comment le corriger. Les corrections demandées par le TP donnent déjà des pistes à chercher :

  • Commentaires inutiles (par exemple « //classe Book ») : bruit, code mort. Solution : supprimer.
  • Doublons de code : risque d'incohérence, maintenance double. Solution : extraire une méthode.
  • Attributs privés sans getters (title, author, borrowed) : classe inutilisable ou accès contourné. Solution : ajouter getTitle(), getAuthor(), isBorrowed().
  • getAvailableItems() qui ne reflète pas l'état des livres empruntés : bug de logique. Solution : filtrer sur l'état emprunté.

Je n'ai pas votre rapport Sonar : les messages exacts viennent de votre analyse.

Q3 : après correction, que doit-on observer ?

Réponse

Relancer sonar-scanner. Les code smells et les bugs liés aux corrections diminuent, la duplication baisse, le Quality Gate peut passer de FAILED à PASSED. Comparer les chiffres avant et après dans le rapport.

Q4 et Q5 : complexité cyclomatique et cognitive

Réponse

Dans la vue Measures du projet, triez les méthodes par complexité cyclomatique, puis par complexité cognitive, et relevez les deux plus élevées de chaque. Stratégie de réduction : découper en sous-méthodes, remplacer les if imbriqués par des retours anticipés, extraire les conditions complexes, remplacer un long switch par du polymorphisme. Après correction, relancer : la complexité de ces méthodes diminue et celle de la classe aussi.

Exercice 1 : McCabe sur un algorithme

1  lire a, b
2  si a > b alors
3     max = a
4  sinon
5     max = b
6  fin_si
7  i = 0
8  tant que i < max faire
9     si i mod 2 = 0 alors
10       s = s + i
11    fin_si
12    i = i + 1
13 fin_faire
14 ecrire s

Calculer la complexité de McCabe avec les deux formules.

Solution
  1. Décisions : si (ligne 2), tant que (ligne 8), si (ligne 9). π = 3, donc C = π + 1 = 4.
  2. Graphe : 8 nœuds (lire et test a > b ; max = a ; max = b ; i = 0 et test tant que ; test mod ; s = s + i ; i = i + 1 ; écrire). 10 arcs. V(G) = 10 - 8 + 2 = 4.

Au moins 4 cas de test pour couvrir les chemins indépendants. Niveau : procédure simple (1 à 10).

Exercice 2 : Halstead sur deux lignes

a = b + c;
d = a * 2;

Calculer n, N, V, D, E, T, B.

Solution
  • Opérateurs : = (2), + (1), * (1), ; (2). n1 = 4, N1 = 6.
  • Opérandes : a (2), b (1), c (1), d (1), 2 (1). n2 = 5, N2 = 6.
  • n = 9, N = 12.
  • V = 12 × log2(9) = 12 × 3,17 ≈ 38,0 bits.
  • D = (4 / 2) × (6 / 5) = 2 × 1,2 = 2,4.
  • E = 38,04 × 2,4 ≈ 91,3. T = 91,3 / 18 ≈ 5,1 s. B = 91,3^(2/3) / 3000 ≈ 0,007.

Exercice 3 : métriques de lignes de code

Un fichier compte 30 lignes physiques : 5 lignes vides, 6 lignes de commentaires, le reste en code. Calculer LOCpro et DC. Comparer aux normes.

Solution
  • LOCpro = 30 - 5 - 6 = 19.
  • DC = 6 / 30 = 0,20, au bas de la plage 0,2 à 0,3 : acceptable.
  • Lignes vides : 5 / 30 ≈ 17 %, dans la plage 10 à 20 %. Lignes de commentaires : 20 %, dans la plage 10 à 30 %.
  • LOCphy = 30 : bien en dessous de 200 à 500, aucun fractionnement nécessaire.

Exercice 4 : métriques CK sur une classe

class Compte extends Produit {
    double solde; String titulaire;
    void depot(double m)   { solde += m; }
    void retrait(double m) { solde -= m; Journal.ecrire("retrait"); Banque.verifier(this); }
    String afficher()      { return titulaire; }
    double interets()      { return solde * 0.02; }
}

Complexités des méthodes : depot 1, retrait 2, afficher 1, interets 1. Produit hérite directement de Object. Calculer WMC, DIT, RFC, CBO (en comptant Produit, Journal, Banque) et LCOM.

Solution
  • WMC = 1 + 2 + 1 + 1 = 5 (faible, entre 0 et 10).
  • DIT : Object, Produit, Compte : 2 (acceptable, de 0 à 4).
  • RFC = 4 méthodes + 2 méthodes externes appelées (Journal.ecrire, Banque.verifier) = 6 (faible).
  • CBO : Produit, Journal, Banque = 3 (faible, de 0 à 5).
  • LCOM : attributs utilisés : depot {solde}, retrait {solde}, afficher {titulaire}, interets {solde}. Paires (6) : (depot, retrait) partage, (depot, afficher) non, (depot, interets) partage, (retrait, afficher) non, (retrait, interets) partage, (afficher, interets) non. Q = 3, P = 3. Comme P n'est pas supérieur à Q, LCOM = 0.

Lecture : classe plutôt saine. La méthode afficher est isolée (elle utilise un autre attribut), signe qu'on pourrait séparer le titulaire dans une classe Client.

Exercice 7 : évaluation pondérée

Facteur Fiabilité = 0,7 × Testabilité + 0,3 × Maturité. Testabilité = 2, Maturité = 3 (notes sur 3). Calculer la fiabilité et l'exprimer en pourcentage.

Solution

Fiabilité = 0,7 × 2 + 0,3 × 3 = 1,4 + 0,9 = 2,3. En pourcentage : 2,3 / 3 ≈ 76,7 %. Les poids d'un même niveau doivent faire 1 (0,7 + 0,3).

Exercice 8 : GQM

Un responsable veut réduire le temps de correction des bugs. Construire l'arbre GQM.

Solution
  • Goal : réduire le temps de correction des bugs dans l'application.
  • Question 1 : le code est-il facile à analyser ? Métriques : complexité cyclomatique moyenne, densité de commentaires, LCOM.
  • Question 2 : le code est-il facile à tester ? Métriques : couverture des tests (A / B), nombre de tests automatisés.
  • Question 3 : combien de temps prend une correction aujourd'hui ? Métriques : durée moyenne entre ouverture et fermeture d'un bug, nombre de régressions.

Chaque métrique répond à une question, chaque question à l'objectif. On ne mesure rien qui ne serve pas le but.

Exercice 9 : erreur, défaut, défaillance

Un développeur écrit if (a = b) au lieu de if (a == b). Identifier l'erreur, le défaut et la défaillance, et dire quelle pratique SQA l'aurait détecté.

Solution
  • Erreur : la faute de frappe du développeur.
  • Défaut : le code contient une affectation à la place d'un test, la condition est mal formée.
  • Défaillance : en exploitation, le programme prend la mauvaise branche (par exemple un solde affiché faux).
  • Détection : revue de code, analyse statique (SonarQube signale ce type d'anomalie), tests unitaires du cas concerné.

Exercice 10 : associer scénario et caractéristique ISO 25010

Pour chaque scénario, donner la caractéristique (et la sous-caractéristique) : (a) la page met 8 secondes à répondre ; (b) l'application ne peut pas lire les fichiers d'un partenaire ; (c) un utilisateur non autorisé lit des données ; (d) un robot s'arrête en sécurité quand un capteur tombe en panne ; (e) l'installation sur un nouveau système se fait sans effort ; (f) le système redémarre seul après une panne ; (g) les tests peuvent être automatisés facilement.

Solution
  • (a) Efficacité des performances, comportement temporel.
  • (b) Compatibilité, interopérabilité.
  • (c) Sécurité, confidentialité.
  • (d) Sécurité des personnes et des biens (safety), comportement fail-safe.
  • (e) Flexibilité, facilité d'installation (adaptabilité).
  • (f) Fiabilité, capacité de récupération.
  • (g) Maintenabilité, testabilité.
