Chapitre 1 : Les bases de données NoSQL

1. Pourquoi les bases relationnelles ne suffisent plus

Prenons une petite boutique en ligne. Au début, trois tables suffisent (Clients, Produits, Commandes) et SQL répond très bien à « quels produits le client X a-t-il achetés ? ». Puis l'entreprise grandit : paiements, avis clients, images HD, vidéos, tags différents d'un produit à l'autre, logs de navigation (clics, recherches, temps passé). Le nombre de jointures augmente et le schéma devient lourd à faire évoluer.

Les points forts du relationnel

  • Utilisé depuis les années 1970, structuré en tables liées par des clés.
  • Intégrité des données : clé primaire, clé étrangère, unicité.
  • Langage standard SQL, gestion des utilisateurs, rôles et droits.
  • Transactions fiables grâce aux propriétés ACID.

Définition : ACID

LettrePropriétéIdéeExemple du cours
AAtomicitéTout ou rienVirement : si le crédit de B échoue, le débit de A est annulé
CCohérenceD'un état valide à un autre état validePas de commande pour un client inexistant
IIsolationLes transactions parallèles n'interfèrent pasLe dernier billet n'est pas vendu deux fois
DDurabilitéAprès commit, la donnée est permanentePaiement confirmé même si le site plante juste après

Les limites du relationnel

  • Temps de réponse : les jointures entre grosses tables ralentissent les requêtes. Une forte normalisation (1FN à 5FN) multiplie les tables et donc les accès disque.
  • Scalabilité limitée : conçues pour un seul serveur (scale-up).
  • Performances dégradées avec le Big Data (milliards d'enregistrements, analyse en temps réel).
  • Transactions lourdes : les verrous (locks) ralentissent quand beaucoup d'utilisateurs accèdent en même temps.
  • Mauvaise prise en charge des données non structurées : images, vidéos, JSON, logs.

Exemple chiffré du cours

Taille des tablesSans indexAvec index optimisés
1M + 5M + 1M20 000 ms500 ms
10M + 50M + 10Mplus de 60 000 ms5 000 ms
100M + 500M + 100Mimpossible60 000 ms

Les index aident beaucoup, mais les performances restent limitées quand les tables atteignent des centaines de millions de lignes.

Rappel : les trois premières formes normales

  • 1FN : chaque attribut contient une valeur unique et atomique (pas de liste, pas de colonnes répétées).
  • 2FN : être en 1FN, et chaque attribut non clé dépend de toute la clé primaire, pas d'une partie seulement.
  • 3FN : être en 2FN, et aucun attribut non clé ne dépend d'un autre attribut non clé (pas de dépendance transitive).

3. Les 3V : Volume, Vélocité, Variété

Le Web a évolué en trois temps. Web 1.0 : pages statiques, le relationnel suffit. Web 2.0 : réseaux sociaux, blogs, e-commerce, les utilisateurs produisent eux-mêmes les données, le volume explose. Web 3.0 : IoT, cloud, streaming, applications en temps réel.

Volume

Quantité gigantesque : pétaoctets, exaoctets. Facebook génère plusieurs pétaoctets par jour.

Vélocité

Vitesse de génération et de traitement : transactions bancaires, capteurs IoT, streaming vidéo, marchés financiers.

Variété

Formats multiples : structurées (tables), semi-structurées (JSON, XML, logs), non structurées (images, vidéos, sons, emails).

Piège

Le cours donne trois V. Si une question demande « les 3V », répondez Volume, Vélocité, Variété. Ne mettez pas Valeur ou Véracité, même si d'autres sources les citent.

4. Définition de NoSQL

Définition

NoSQL signifie « Not Only SQL ». C'est une catégorie de bases de données non relationnelles conçues pour gérer des données non structurées, semi-structurées ou massives, là où SQL montre ses limites. Elles proposent des modèles de stockage flexibles et évolutifs, adaptés au Big Data, aux applications web à grande échelle et à l'IoT.

Les quatre grandes familles (schéma « topologies » du cours) sont : clé-valeur (Redis, DynamoDB), documents (MongoDB, CouchDB), colonnes (Cassandra, HBase) et graphes (Neo4j). Dans ce cours, on étudie MongoDB, donc la famille documents.

5. Les principes du NoSQL

a) Modèle flexible (schema-less)

Pas de schéma imposé à l'avance. En SQL, ajouter l'âge d'un client demande ALTER TABLE Clients ADD Age INT;. En NoSQL, un document peut simplement avoir un champ age et un autre non, sans migration.

b) Scalabilité horizontale : sharding et load balancing

  • Sharding (fragmentation) : la base découpe les données en shards. Serveur A : produits A à M, serveur B : N à Z. Si on ajoute un serveur C, une partie des données est redistribuée.
  • Load balancing : un répartiteur envoie chaque requête au bon serveur.

Exemple : plateforme de vidéos

Trois serveurs : A (profils utilisateurs), B (métadonnées des vidéos), C (logs de visionnage). La sortie d'une série très attendue sature le serveur C. Solution : on ajoute un serveur D, la base redistribue automatiquement une partie des logs de C vers D, et le load balancer équilibre la charge. Aucun serveur n'est saturé et la plateforme reste fluide.

c) Haute disponibilité et performance

  • Réponse rapide même sous forte charge (faible latence).
  • Réplication : les données sont copiées sur plusieurs serveurs. Écrite sur A, la donnée est répliquée sur B et C. Si A tombe, B ou C répondent.
  • Index et structures adaptées (arbres B+, tables de hachage) : une recherche sur un champ email indexé prend quelques millisecondes, même sur des millions d'enregistrements.

d) Pas de jointures complexes

Pour aller plus vite, on duplique ou on imbrique les données dans un même document JSON. C'est la dénormalisation, à l'opposé de la normalisation du relationnel.

e) Théorème CAP

Définition : CAP (Brewer, 2000)

Dans un système distribué, il est impossible de garantir en même temps les trois propriétés :

  • Consistency (cohérence) : toutes les répliques montrent le même état au même instant, chaque lecture retourne la dernière écriture.
  • Availability (disponibilité) : chaque requête reçoit une réponse, même en cas de panne partielle.
  • Partition tolerance (tolérance au partitionnement) : le système continue de fonctionner même si le réseau est coupé en plusieurs parties.

Lors d'une partition réseau, il faut sacrifier la cohérence ou la disponibilité :

ChoixCe qu'on gardeCe qu'on sacrifieConséquence
CPCohérence, partitionDisponibilitéDonnées toujours exactes, mais erreur ou attente possible
APDisponibilité, partitionCohérence (temporairement)Service toujours là, mais données parfois périmées

Exemple : hôtel d'Agadir, une seule chambre libre

Deux serveurs : Paris (touristes européens) et Rome (touristes italiens). Une panne coupe la communication entre eux, et deux clients veulent la dernière chambre.

  • Système CP : Paris accepte et bloque la chambre, Rome refuse ou met en attente. Pas de double vente, mais le client de Rome n'est pas servi.
  • Système AP : les deux serveurs acceptent. Deux clients croient avoir la chambre (incohérence temporaire). Au retour du réseau, on annule l'une des réservations, on applique « premier arrivé, premier servi » ou on déplace un client dans une chambre équivalente.

f) Modèle BASE

Définition : BASE

  • Basically Available : le système répond toujours, même si toutes les données ne sont pas immédiatement cohérentes.
  • Soft-state : l'état peut changer au fil du temps, même sans nouvelle saisie, car la cohérence se construit progressivement.
  • Eventually consistent : les données finiront par être cohérentes, mais pas forcément juste après une mise à jour.

6. ACID contre BASE

CritèreACIDBASE
PrioritéCohérence avant disponibilitéDisponibilité avant cohérence stricte
ÉvolutivitéVerticaleHorizontale
FlexibilitéMoins flexible : bloque des enregistrements pour d'autres applicationsPlus flexible : plusieurs applications peuvent mettre à jour le même enregistrement
Gros volumesPerformances en baisseGère de grandes quantités de données non structurées à haut débit
SynchronisationOui, avec un délaiPas de synchronisation stricte
AvantageDonnées toujours exactes, transactions fiablesPerformance et scalabilité élevées

ExemplesPostgreSQL, MySQL, OracleCassandra, DynamoDB, MongoDB

Quel modèle choisir ?

  • Acheter le dernier billet de train : ACID (transaction atomique, jamais vendu deux fois).
  • Ajouter un article au panier alors qu'il en reste un en stock : BASE (le système accepte tout de suite, la synchronisation vient après).
  • Poster un tweet : BASE (des utilisateurs éloignés ne le voient pas au même instant, ce n'est pas grave).

Chapitre 2 : MongoDB

1. Définition et historique

Définition

MongoDB est un SGBD NoSQL orienté documents, créé pour gérer de grandes quantités de données de façon flexible, rapide et évolutive. Au lieu de tables et de lignes, il stocke des documents JSON/BSON (Binary JSON). Un document peut contenir du texte, des nombres, des tableaux, des documents imbriqués, sans schéma rigide défini d'avance.

2. L'écosystème

  • Le cœur : MongoDB Database, en auto-hébergé (Self-Managed / Enterprise), dans le cloud avec Atlas, ou en version mobile.
  • Outils autour : Compass (interface graphique officielle), BI Connectors (Tableau, Power BI), Charts (graphiques).
  • Realm : plateforme backend (Serverless Query API, Serverless Functions, Database Triggers, Real-Time Sync).
  • Utilisateurs connus : eBay, Uber, GitHub, LinkedIn, Adobe, Cisco, IBM, SAP, Forbes, New York Times.

3. Architecture interne

  1. Client : votre programme (Python, Java, Node.js) qui parle à MongoDB via un driver officiel.
  2. Serveur : le processus mongod reçoit et route les requêtes. Le Query Engine analyse, optimise et exécute, avec les index et les pipelines d'agrégation. Le moteur WiredTiger (par défaut) gère lecture et écriture avec un cache en RAM, un journal (Write Ahead Log) pour la durabilité et la compression.
  3. Disque : documents en BSON, chacun avec son _id, collections, index stockés à côté.
  4. Réplication et sharding : replica set (copies synchronisées pour la tolérance aux pannes) et sharding (partitionnement horizontal pour les très gros volumes).

En local, deux éditions : Community Server (licence SSPL, libre, sans support officiel, pour projets personnels ou académiques) et Enterprise Server (licence payante, support officiel, sécurité et monitoring avancés, production à grande échelle).

5. Avantages de MongoDB

  • Flexibilité du schéma : des documents différents dans la même collection, idéal pour les projets agiles.
  • Scalabilité horizontale par sharding.
  • Haute disponibilité par replica sets : le primaire reçoit les écritures, les secondaires sont des copies. Si le primaire tombe, un secondaire prend le relais automatiquement.
  • Multi-plateforme : drivers (Java, Python, Node.js, C#), cloud (Atlas) ou local, Compass et Charts.
  • Richesse : index avancés (simples, composés, géospatiaux, textuels, TTL), pipeline d'agrégation, transactions ACID depuis la version 4.0.

6. Les concepts de base

Hiérarchie

SQL : Base, Tables, Lignes, Colonnes.
MongoDB : Base, Collections, Documents, Champs.

  • Base de données : le conteneur principal, indépendant des autres. Un serveur en héberge plusieurs (shop, school), chacune avec ses collections.
  • Bases système : admin (administration), local (réplication), config (sharding). Ne pas y toucher.
  • Collection : équivalent d'une table, sans schéma fixe, indexable, jusqu'à de très gros volumes grâce au sharding. Collections spéciales : system.indexes et system.profile (créées automatiquement).
  • Document : équivalent d'une ligne, paires clé/valeur, maximum 16 Mo, champ _id unique et obligatoire (généré automatiquement si absent).
  • Champ : équivalent d'une colonne. Types : string, nombre (int, double, decimal128), booléen, date, tableau (array), sous-document.
// Même collection "produits", deux documents différents
{ "id": 1, "nom": "Laptop X", "prix": 1200, "categorie": "Informatique" }
{ "id": 2, "nom": "Smartphone Y", "prix": 800, "marque": "Y", "stock": 25 }

// Document imbriqué : plus besoin de table Avis ni de jointure
{ "nom": "Laptop X", "prix": 1200,

Chapitre 3 : Récupérer les documents avec find()

Syntaxe

db.collection.find(query, projection, options)

Équivalent de SELECT ... WHERE. Renvoie un curseur vers les documents qui correspondent. Les trois paramètres sont optionnels : pas de paramètre ou {} = tous les documents.

1. Filtres simples

db.Films.find()                                   // tous les documents
db.Films.find({ titre: "Titanic" })               // égalité
db.Films.find({ _id: ObjectId("68e975d6b51b450edacebea4") })
db.Films.find({ titre: "Inception", annee: 2010 })  // ET implicite

Plusieurs champs dans le même objet = ET logique. C'est l'équivalent de $and.

2. Opérateurs logiques et de comparaison

db.Films.find({ $and: [ { titre: "Inception" }, { annee: 2010 } ] })
db.Films.find({ $or: [ { realisateur: "Christopher Nolan" }, { genre: "Science-fiction" } ] })
OpérateurSignificationExemple
$eqégal{ annee: { $eq: 2010 } }
$gt / $gtesupérieur / supérieur ou égal{ annee: { $gt: 2010 } }
$lt / $lteinférieur / inférieur ou égal{ annee: { $lt: 2010 } }
$indans une liste de valeurs{ realisateur: { $in: ["Christopher Nolan", "James Cameron"] } }
$ne, $nindifférent, pas dans la liste (non détaillés dans le cours, mais utiles){ annee: { $ne: 2010 } }

Intervalle (entre 15 et 18 inclus) : deux opérateurs dans le même sous-objet.

db.Etudiants.find({ moyenne: { $gte: 15, $lte: 18 } })

3. Expressions régulières

db.Films.find({ $and: [ { annee: { $gt: 2000 } }, { titre: /ar/i } ] })
db.Films.find({ titre: { $regex: "Love" } })      // forme équivalente avec $regex

4. Documents imbriqués : la notation pointée

db.Etudiants.find({ "adresse.ville": "Agadir" })
db.Etudiants2.find({ "resultats.module3": { $gte: 15 } })

Piège

Les guillemets autour de "adresse.ville" sont obligatoires. Sans eux, c'est une erreur de syntaxe.

5. Projection

La projection est le deuxième argument : 1 pour inclure un champ, 0 pour l'exclure.

db.Etudiants2.find({}, { nom: 1, "adresse.ville": 1, _id: 0 })

// filtre + projection
db.Etudiants2.find(
  { "resultats.module3": { $gte: 15 } },
  { nom: 1, "resultats.module3": 1, _id: 0 }
)

À retenir

  • L'_id s'affiche par défaut : écrire _id: 0 pour le cacher.
  • On ne mélange pas inclusion et exclusion, sauf pour _id.

6. Tableaux

OpérateurRôleExemple
(valeur seule)Le tableau contient cette valeurfind({ notes: 15 })
$inAu moins une des valeursfind({ notes: { $in: [16, 18] } })
$allToutes les valeursfind({ modules: { $all: ["Base de données", "Réseaux"] } })
$sizeExactement N élémentsfind({ modules: { $size: 3 } })
$elemMatchUn même élément vérifie plusieurs conditionsvoir ci-dessous

$elemMatch sur un tableau de sous-documents

// étudiants ayant au moins une note >= 16 en Statistiques
db.Etudiants4.find({
  resultats: { $elemMatch: { module: "Statistiques", note: { $gte: 16 } } }
})

MongoDB parcourt le tableau resultats de chaque étudiant et cherche au moins un élément qui vérifie toutes les conditions. Si oui, il renvoie le document entier, pas seulement l'élément.

Afficher seulement l'élément trouvé : l'opérateur positionnel $

db.Etudiants4.find(
  { "resultats.module": "Statistiques", "resultats.note": { $gte: 16 } },
  { "resultats.$": 1, nom: 1, _id: 0 }
)

Le $ ne s'applique qu'aux tableaux. Il ne marche pas sur un champ simple ni sur un sous-document qui n'est pas un tableau.

$all sur un tableau d'objets

db.Etudiants4.find({ "resultats.module": { $all: ["Base de données", "Réseaux"] } })

db.Etudiants4.find({
  resultats: { $all: [
    { $elemMatch: { module: "Base de données" } },
    { $elemMatch: { module: "Réseaux" } }
  ] }
})

$size

db.Classes.find({ etudiants: { $size: 2 } })
db.Classes.find({ etudiants: { $elemMatch: { modules: { $size: 3 } } } })  // tableau imbriqué

$size ne fait que de l'égalité. Quand le tableau est plus profondément imbriqué (etudiants.modules), on passe par $elemMatch.

7. Trier, limiter, ignorer

db.Etudiants.find().sort({ nom: 1 })               // croissant
db.Etudiants.find().sort({ nom: -1 })              // décroissant
db.Etudiants.find().sort({ filiere: 1, nom: 1 })   // filière puis nom
db.Etudiants.find().limit(2)
db.Etudiants.find({ filiere: "Informatique" }).skip(2)
db.Etudiants.find().sort({ nom: 1 }).skip(2).limit(2)   // pagination

// filtre + projection + tri
db.Etudiants.find({ filiere: "Informatique" }, { _id: 0, nom: 1, modules: 1 }).sort({ nom: 1 })
  • Sans sort(), MongoDB ne garantit aucun ordre.
  • Trier sur un champ tableau utilise la première valeur du tableau, sans trier à l'intérieur.
  • L'ordre réel est toujours tri, puis skip, puis limit.
